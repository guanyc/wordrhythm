# Word Rhythm

Brand hub for the **Word Rhythm** Bible app family — `Word Rhythm: KJV / ASV / WEB / Biblia RVR / 和合本 / Bíblia AA`.
Slogan: *Scripture for the rhythm of everyday life.*

Built with **Next.js 15 (App Router) + TypeScript + Tailwind CSS**. The site is a
static export; the only server-side code is a small Worker that renders the
verse URLs the export cannot hold (see [KJV reading routes](#kjv-reading-routes-kjv)).

## Local development

```bash
npm install
npm run dev      # http://localhost:3000
```

## Build

```bash
npm run build      # produces a static site in ./out
```

> This project uses `output: "export"`, so it builds to plain static files in
> `out/`. Look at the result with `npm run preview` (http://localhost:3001),
> which resolves paths the way the asset binding does — `npm run dev` cannot
> answer `/kjv/<book>/<chapter>/<verse>`, because those pages are files that
> `scripts/kjv-verses.mjs` writes after the build, not routes.

## Deploy to Cloudflare (from GitHub)

The site is a Worker named `wordrhythm`. The export in `out/` is uploaded as
static assets through the `ASSETS` binding in `wrangler.jsonc`, and
`worker/index.ts` answers the verse URLs no file covers.

It is connected to this GitHub repository, so **a push to `main` is a deploy**:
Cloudflare runs `npm run build` and publishes. There is no GitHub Actions
workflow involved, and nothing to trigger by hand — the change is live a couple
of minutes after the push. `npm run deploy` (`wrangler deploy`) does the same
from a terminal, uploading whatever is in `out/` locally, and is the path for a
manual deploy or a fix that must go out without a commit.

A push is therefore a production action. Look first:

```bash
npm run build && npm run preview
```

## KJV reading routes (`/kjv`)

`https://wordrhythm.app/kjv/<book>/<chapter>/<verse>` is the address a verse
shared from the KJV Android app points at, and it is registered as an Android
App Link (`autoVerify`, `public/.well-known/assetlinks.json`). On a device with
the app installed the OS opens the reader and the site is never hit.

| Path | Rendered by | Indexable |
|---|---|---|
| `/kjv`, `/kjv/<book>` | static export (`app/kjv/…`) | yes |
| `/kjv/<book>/<chapter>` | static export — 1,189 pages | yes, in `sitemap.xml` |
| `/kjv/<book>/<chapter>/<verse>` | `scripts/kjv-verses.mjs` — 31,102 files written into `out/` | no (`noindex, follow`, canonical → chapter) |
| a verse past the end of its chapter | `worker/index.ts` → 302 to the chapter | no |

Verse files are generated by a post-build script rather than as React routes:
they are the same template the Worker renders (`lib/verse-page.mjs`, so a
pre-rendered verse and a fallback verse cannot look different), they never
hydrate, and 31,102 of them cost about 10 seconds of build time as strings
versus minutes as routes. The Worker is now only the fallback for an address
with no file.

That output is **34,126 files** and about 224 MB, which is past Cloudflare's
20,000-file ceiling for static assets on the Workers Free plan — deploying this needs Workers Paid
($5/month, 100,000 files). Drop `scripts/kjv-verses.mjs` from the `build` script
to go back to Worker-rendered verses and the free plan.

The plan went to Workers Paid on 2026-11-08 and the full tree is deployed: 152 s
end to end, of which 100 s was uploading 33,935 changed assets (wrangler reuses
hashes it has seen before, so later deploys only send what changed).

Their stylesheet is `public/kjv/verse.css`, linked rather than inlined: the
same 2.3 KB repeated across 31,102 pages was 72 MB of the deploy and meant
restyling one file instead of 31,102. Editing it restyles every verse page.

The pages also stay on the right side of Play policy: the verse is the content,
the install link is an offer beside it — nothing redirects to the store.

Text lives in `public/kjv-data/` (66 per-book files + `books.json`, generated by
`scripts/build-kjv.py` from the Android app's `kjv_bible.json`). Re-run it after
the app's KJV data changes:

```bash
python3 scripts/build-kjv.py   # expects /Users/guanyc/StudioProjects/KJV_CUV
```

## Project structure

```
app/
  layout.tsx              # root layout + metadata
  globals.css             # palette (CSS vars) + rhythm equalizer animation
  page.tsx                # home: hero + rhythm flow + version grid + screenshot strip
  versions/page.tsx       # all translations
  versions/[slug]/page.tsx# per-version detail: icon, Play link, screenshots
  take-a-break/page.tsx
  kjv/page.tsx            # /kjv book index
  kjv/[book]/page.tsx     # chapter grid
  kjv/[book]/[chapter]/page.tsx  # the chapter itself (1,189 static pages)
components/               # Header, Footer, Hero, RhythmFlow, VersionCard, Screenshots
lib/versions.ts           # single source of truth for the version grid
lib/kjv.ts                # KJV book/chapter lookup + app-link URLs
lib/verse-page.mjs        # one verse page, shared by the build script and the Worker
worker/index.ts           # 302 for a verse past the end of its chapter, 404 body
scripts/kjv-verses.mjs    # writes 31,102 verse pages into out/ after next build
public/apps/<slug>/       # icons + screenshots pulled from Google Play
public/kjv/verse.css     # stylesheet shared by all 31,102 verse pages
public/kjv-data/          # generated: 66 books of KJV text + books.json
DESIGN.md                 # brand analysis + site design
```

## Adding a translation

1. Add an entry in `lib/versions.ts` (`slug`, `code`, `name`, `listing`,
   `storeTitle`, `language`, `summary`, `status`, optional
   `package`/`playUrl`).
2. Drop its Play Store assets into `public/apps/<slug>/`: `icon.png` plus
   `01.jpg`–`04.jpg` screenshots (the `shots()` helper in `lib/versions.ts`
   wires the paths automatically).
